# 系统架构文档 — 安诊保 AI 副驾

> **文档状态**：当前有效 · 分层架构与数据流已与当前代码一致（RAG 生产链路见 docs/rag.md）
> 最后校准：2026-08-17


## 1. 架构概述

安诊保 AI 副驾是一款面向保险代理人的智能销售助手工作台。系统通过 AI 驱动的产品问答、客户画像、话术生成、合规检查等核心能力，帮助保险代理人提升销售效率与专业水平。

### 架构风格

- **前后端分离**：前端（React SPA）与后端（FastAPI）通过 RESTful API + SSE 进行通信，职责清晰、独立部署。
- **微服务化预留**：当前阶段采用单体架构（Modular Monolith），但在模块边界、数据访问层做了严格的解耦设计，未来可按业务域拆分为独立微服务。
- **AI-Native 设计**：AI 能力不是附属功能，而是贯穿整个业务流程的核心基础设施。所有业务模块均可通过统一的 AI Gateway 调用大模型能力。

### 架构原则

| 原则       | 说明                                                                 |
| ---------- | -------------------------------------------------------------------- |
| **安全**   | JWT 认证 + RBAC 权限 + 数据脱敏 + 合规引擎 + Prompt Injection 防护 + 审计日志 |
| **可维护** | 分层架构（Router → Service → Repository → Model）、统一错误处理、结构化日志     |
| **可扩展** | AI Gateway 统一接口、Provider 可插拔、RAG Pipeline 可配置、水平扩展预留     |
| **AI-Native** | AI 能力深度融入业务流程，而非外挂式集成                              |

## 3. 前端架构

### 3.1 技术栈

| 类别       | 技术选型                    | 用途                                       |
| ---------- | --------------------------- | ------------------------------------------ |
| 框架       | React 19 + TypeScript 5.x  | UI 构建、类型安全                           |
| 构建工具   | Vite 6                      | 极速 HMR、按需编译、生产优化                   |
| 样式       | Tailwind CSS 4              | 原子化 CSS、JIT 编译、Design Token           |
| 组件库     | shadcn/ui                   | 可定制的高质量 React 组件（非黑盒）             |
| 数据请求   | TanStack React Query v5     | 服务端状态管理、缓存、自动重试、乐观更新          |
| 路由       | React Router v7             | 声明式路由、嵌套路由、路由守卫、懒加载           |
| 全局状态   | Zustand                     | 轻量客户端状态管理（主题、侧边栏、用户偏好等）   |
| 表单       | React Hook Form + Zod       | 高性能表单管理 + Schema 校验                   |
| HTTP 客户端 | 原生 Fetch（封装）           | API 通信、SSE 流式响应                        |
| 图标       | Lucide React                | 一致的图标风格                                |
| 代码规范   | ESLint + Prettier + Husky   | 代码质量保障                                  |

### 3.3 状态管理策略

本系统采用**分层状态管理**策略，根据数据来源和生命周期选择最合适的管理方案：

```
┌─────────────────────────────────────────────────────────────┐
│                      状态管理分层                             │
├─────────────────────┬───────────────────────────────────────┤
│  服务端状态          │  TanStack React Query                  │
│  (Server State)     │  · 自动缓存与过期                      │
│                     │  · 后台自动刷新                        │
│                     │  · 乐观更新（Optimistic Update）         │
│                     │  · 分页与无限滚动                       │
│                     │  用途：API 数据（客户列表、知识库、对话历史）│
├─────────────────────┼───────────────────────────────────────┤
│  客户端全局状态       │  Zustand                               │
│  (Client Global)    │  · 极简 API、无 Provider 包裹            │
│                     │  · 支持 middleware（persist, devtools）  │
│                     │  · 选择性订阅（避免不必要的重渲染）        │
│                     │  用途：用户信息、UI 偏好、主题、侧边栏     │
├─────────────────────┼───────────────────────────────────────┤
│  表单状态            │  React Hook Form + Zod                 │
│  (Form State)       │  · 非受控组件、高性能                    │
│                     │  · 实时 Schema 校验                     │
│                     │  用途：登录表单、客户信息录入、知识库上传   │
├─────────────────────┼───────────────────────────────────────┤
│  组件局部状态         │  useState / useReducer                 │
│  (Component Local)  │  用途：弹窗开关、Tab 切换、临时 UI 状态   │
└─────────────────────┴───────────────────────────────────────┘
```

### 4.4 中间件

中间件按执行顺序排列，形成请求处理的「洋葱模型」：

```
HTTP Request
    │
    ▼

                       ▼
┌─────────────────────────────────────────────────┐
│  2. Request ID Middleware                          │
│     · 为每个请求生成唯一 X-Request-ID               │

└──────────────────────┬──────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────┐
│  3. Rate Limiting Middleware                       │
│     · 基于 Redis 的滑动窗口限流                     │
│     · 全局限流 + 按 User / IP 分别限流              │
│     · AI 接口单独限流（更严格的配额）                 │
└──────────────────────┬──────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────┐
│  4. Auth Middleware (JWT)                          │
│     · 从 Authorization Header 提取 Bearer Token   │
│     · 验证签名、过期时间、黑名单                      │

└──────────────────────┬──────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────┐
│  5. Audit Logger Middleware                        │
│     · 记录所有写操作（POST/PUT/DELETE）              │
│     · 审计内容：操作人、操作类型、目标资源、变更摘要   │

                       ▼

│     · 全局异常捕获                                  │

                 Router → Service → ...
                       │
                       ▼
```

### Prompt 管理策略

- **代码内 Prompt**：系统核心 Prompt（如合规检查）以 Python 代码形式维护在 `ai/prompts/` 目录，享受类型检查和版本控制。
- **文件外挂 Prompt**：业务 Prompt 模板以 YAML 格式存储在 `prompts/` 目录，支持非开发人员修改，热加载无需重启。
- **Prompt 版本管理**：每个 Prompt 模板包含 `version` 字段，支持 A/B 测试和回滚。

## 6. RAG 架构

RAG（Retrieval-Augmented Generation，检索增强生成）是安诊保 AI 副驾的核心能力基础，确保 AI 回答基于权威知识库内容，而非「幻觉」。

### 6.1 RAG Pipeline 全流程

```
═══════════════════════════════════════════════════════════
                    离线索引流程（Ingestion Pipeline）
═══════════════════════════════════════════════════════════

文档上传 (PDF/Word/Excel/TXT/HTML)
    │
    ▼
┌──────────────┐
│ 1. 文档加载   │  支持格式：PDF、DOCX、XLSX、TXT、HTML、Markdown
│   (Loader)   │  提取纯文本 + 元数据（标题、章节、页码）
└──────┬───────┘
       ▼
┌──────────────┐
│ 2. 文本解析   │  清洗噪音（页眉页脚、水印、目录）
│   (Parser)   │  保留结构信息（标题层级、列表、表格）
└──────┬───────┘
       ▼
┌──────────────┐
│ 3. 文本分块   │  策略：
│  (Chunking)  │  · 固定长度分块（chunk_size=512, overlap=64）
│              │  · 语义分块（按段落/章节自然边界切分）
│              │  · 混合策略（先按章节切分，超长章节再按固定长度切分）

       ▼
┌──────────────┐

└──────┬───────┘
       ▼
┌──────────────────────────────────────────┐
│ 5. 存入 PostgreSQL (pgvector)             │
│    · 文档元数据表 (knowledge_documents)    │
│    · 文档分块表 (knowledge_chunks)         │
│      - chunk_text: 分块文本               │
│      - embedding: vector(1536)            │
│      - metadata: JSONB (来源、页码等)     │
│      - document_id: 外键                  │
│      - created_at: 时间戳                 │

═══════════════════════════════════════════════════════════

    │
    ▼
┌──────────────────┐
│ 1. Query 预处理    │  · Query 改写/扩展（可选，LLM 辅助）
│                  │  · 意图识别（产品问答 / 话术生成 / 通用咨询）
└──────┬───────────┘
       ▼
┌──────────────────┐
│ 2. Query Embedding│  调用 AI Gateway.embed() 生成查询向量
└──────┬───────────┘
       ▼
┌──────────────────────────────────────────────┐
│ 3. Hybrid Search (混合检索)                    │
│                                               │
│  ┌─────────────────┐  ┌─────────────────────┐ │
│  │ 向量检索 (ANN)   │  │ BM25 关键词检索      │ │

│  │ cosine similarity│  │ 全文搜索索引         │ │
│  │ Top-K=20        │  │ Top-K=20            │ │
│  └────────┬────────┘  └──────────┬──────────┘ │
│           │                      │             │
│           └──────────┬───────────┘             │
│                      ▼                         │
│           Reciprocal Rank Fusion (RRF)          │
│           合并排序 → Top-K=10                   │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────┐

│                  │  从 10 条精排到 5 条
└──────┬───────────┘
       ▼
┌──────────────────┐

       ▼
┌──────────────────┐
│ 6. Context 组装   │  将检索结果格式化为 LLM Context

       ▼
┌──────────────────┐
│ 8. 引用溯源       │  在 AI 回答中标注引用的知识条目
```

### 6.2 RAG 关键设计决策

| 决策点           | 选择                   | 理由                                                |
| ---------------- | ---------------------- | --------------------------------------------------- |
| 向量数据库         | PostgreSQL + pgvector  | 减少技术栈复杂度，与业务数据同库，事务一致性好，维护成本低    |
| 分块策略           | 语义 + 固定长度混合     | 保险文档结构化程度高，需保留章节完整性                       |
| 检索策略           | Hybrid Search (RRF)    | 向量检索捕获语义相似性，BM25 捕获关键词精确匹配，两者互补      |
| 重排序             | Cross-Encoder          | 相比纯向量检索，显著提升 Top-K 精度                        |
| Embedding 模型      | 复用 AI Gateway        | 统一管理，灵活切换                                       |

### 11.3 Demo 模式技术实现

```python
# backend/app/core/config.py (示意)
class Settings(BaseSettings):
    demo_mode: bool = False
    ai_provider: str = "deepseek"  # demo_mode=True 时自动覆盖为 "mock"

    @property
    def effective_ai_provider(self) -> str:
        return "mock" if self.demo_mode else self.ai_provider

# backend/app/ai/gateway.py (示意)
class AIGateway:
    def __init__(self, settings: Settings):
        provider_name = settings.effective_ai_provider
        self.provider = self._create_provider(provider_name)

# backend/app/main.py (示意)
@app.on_event("startup")
async def startup():
    if settings.demo_mode:
        await seed_demo_data()  # 自动导入 Seed 数据
```
